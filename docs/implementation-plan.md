# План реализации

Порядок работ, критерии приёмки и грабли. Порядок выбран так, чтобы каждая
ступень давала пользу сама по себе и не зависела от ещё не решённых вопросов.

## Этап 0 — прототип расписания (сделано 2026-11-17)

Файлы: `parser.py`, `ics.py`, `main.py`, фикстура `fixtures/735-1.html`.

Сделано:

- Парсер разметки `timetable.tusur.ru` (мобильные таблицы + модалки).
- Генератор `.ics`: `VTIMEZONE Asia/Tomsk (+0700)`, `VALARM −30 мин`,
  стабильные UID, `SEQUENCE` по хешу содержимого, свёртка ≤75 октетов.
- CLI: `--fixture` (без сети), `--faculty`, `--weeks-ahead`, `--from-cache`,
  пауза между запросами, локальный кэш HTML.

Проверено фактически:

- фикстура текущей недели (850) → **3 события**: экзамены ТВиМС 18.11 13:15 и
  15:00 (улк 310), зачёт «Численные методы» 20.11 10:40 (улк 408);
- живой прогон на 5 недель → **22 события** (неделя 851 даёт 19 пар);
- повторный прогон с тем же `--state` → `SEQUENCE` не растёт;
- подмена аудитории в фикстуре → `SEQUENCE:1` только у изменённых пар;
- структура `.ics`: баланс `BEGIN/END`, CRLF, макс. длина строки 73 октета.

Осталось на этом этапе: ничего, код рабочий, но в репозиторий не выложен.

## Этап 1 — дедлайны из фида СДО

Шаги:

1. `feed.py`: скачать фид по `~/.config/tusur/calendar.url`, развернуть строки
   (`\r\n` + пробел **или таб**), распарсить `VEVENT`.
2. Нормализовать: `uid`, `summary`, `dtstart/until` (UTC → Томск), `categories`
   (предмет), `description` (текст задания с LaTeX), ссылки `Links:` внутри
   описания.
3. `state.json` для дедлайнов: `uid → {hash(dtstart+summary), seq}`;
   `diff.json`: `new / changed / gone`.
4. `deadlines.ics`: те же события, но с `VALARM` (−1 день, −3 часа) и
   человекочитаемым `SUMMARY` (`ЧМ: тест закрывается …`).
5. Отдельный `deadlines.md` (или json) — вход для планировщика задач и для
   `math-solver`: условие целиком, формулы уже в LaTeX.

Критерий приёмки: на текущем фиде 19 событий; повторный прогон даёт пустой
дифф; искусственный сдвиг даты в фикстуре даёт ровно одно `changed`.

Проверки: прогон на сохранённом фиде, затем один живой запрос; сравнить
количество событий с тем, что показывает СДО в браузере.

## Этап 2 — публикация через GitHub Actions (решение принято)

Сборка и публикация идут в облаке, локального `push` нет.

Шаги:

1. Репозиторий `tusur-schedule` (публичный — минуты Actions бесплатны),
   ветка `main`, `schedule-735-1.ics` в корне. Pages = Deploy from a branch.
2. `ics.py` / `main.py`: добавить `--state-from <файл>` — читать SEQUENCE из
   уже закоммиченного `.ics`, а не из `state.json` (иначе на раннере дубли).
3. `.github/workflows/update.yml`: `schedule` раз в сутки + `workflow_dispatch`,
   `permissions: contents: write`, `concurrency`, шаги: checkout → python → `main.py`
   → `git diff --quiet && exit 0` → commit + push.
4. Секреты (authtoken фида СДО) — в `Settings → Secrets`, не в файлах.
5. **Первый запуск — только `workflow_dispatch`**, чтобы проверить, пускает ли
   `timetable.tusur.ru` облачный IP. Успех → крон включается; таймаут → остаётся
   локальный `systemd`-таймер, генератор и workflow те же.

Критерий приёмки: `curl -I https://z0den.github.io/tusur-schedule/schedule-735-1.ics`
→ `content-type: text/calendar`; подписка в календаре показывает пары; повторный
прогон **не создаёт коммит** (дифф пустой) и не плодит дубли в календаре.

Проверки: `python3 -c "import yaml; yaml.safe_load(open('.github/workflows/update.yml'))"`;
`actionlint` в системе нет — при желании поставить или обойтись этой проверкой.

## Этап 3 — напоминания и диффы

Шаги:

1. После сборки — если `diff.json` не пуст, записать его в репозиторий
   (`diff.json` — компактная сводка изменений) и отдать наружу: новая пара,
   перенос, отмена, новый дедлайн, сдвиг срока.
2. Запуск: тот же workflow; при выключенном ноутбуке обязанности не теряются —
   `.ics` в календаре всё равно даёт напоминания. Уведомления в чат (если будут)
   делаются локально по `diff.json`, потому что облако до телефона не достанет.

Критерий приёмки: подмена фикстуры даёт ровно один алерт на изменение, без
повторов при повторных прогонах.

## Этап 4 — материалы курсов (нужна сессия)

Шаги:

1. `auth.py`: Playwright в открытом режиме, человек логинится в SSO сам,
   сохраняем `storageState` в `~/.config/tusur/state.json` (600). Пароль не
   сохраняется.
2. Чтение курса: `POST /lib/ajax/service.php?sesskey=…&info=core_course_get_contents`
   (sesskey берётся из `M.cfg` любой страницы) — либо клик-путь, если API не
   отдаст модуль.
3. Скачивание файлов: `pluginfile.php` ссылки из структуры курса.
4. `tools/sdo_import.py`: разложить по `math-solver/materials/<предмет>/`,
   `pdftotext` → если текстового слоя нет, `tesseract`; сделать `.md` с текстом
   и формулами; дописать строку в `INDEX.md` (`предмет | путь | что там`).
5. Не писать в `materials/` из агентов — только скрипт (в проекте стоит запрет).

Критерий приёмки: файл лекции лежит в `materials/<предмет>/`, строка в
`INDEX.md` описывает содержание и содержит 1–2 формулы; агент находит материал
grep'ом по `INDEX.md`; повторный прогон не создаёт дублей (сверка по имени и
размеру файла).

## Этап 5 — Vikunja: задачи и синхронизация (частично сделано)

Сделано 2026-11-17: Vikunja 2.8.0 поднята (`docker run`, порт 3456, SQLite в
`./db`), пользователь `Blesk`, проект `Inbox`, MCP подключён к OpenCode и
проверен (27 инструментов, `projects_list` отвечает).

Осталось:

1. **Compose вместо `docker run`**: тег `2.8.0` вместо `latest`,
   `restart: unless-stopped` в файле (сейчас политика поставлена через
   `docker update` и сбросится при пересборке), фиксированное имя контейнера,
   `VIKUNJA_SERVICE_PUBLICURL=http://100.121.145.104:3456/`.
2. **CalDAV-токен** в Settings → CalDAV, подключение Tasks.org
   (`http://100.121.145.104:3456/dav/`, логин `Blesk`), проверка `PROPFIND`.
3. **Проекты по предметам** вместо одного `Inbox`.
4. **Заливка дедлайнов**: `feed.py` → задачи Vikunja (`tasks_create` или REST),
   внешний ключ = `UID` фида, повторный прогон обновляет, а не дублирует.
5. **Планировщик**: свободные окна из расписания + укладка EDF + запись шагов.

Критерий приёмки этапа 5: задача, созданная агентом, видна в Tasks.org на

## Этап 6 — ИИ-планировщик (решение принято, реализация не начата)

План составляет модель раз в сутки и пишет в Vikunja через MCP; код проверяет
результат. Схема и пороги — `idea-and-architecture.md` §7.2.

Порядок работ:

1. **`build_context.py`** — собрать `.state/plan-input.json`: свободные окна на
   14 дней (пары + буферы УЛК/физкультура/неизвестно), открытые дедлайны,
   текущий план, ограничения, `pinned`. Детерминированно, без модели.
2. **`validate_plan.py`** — проверки из таблицы §7.2, вывод списком нарушений
   в машинном виде. Пишется и тестируется **до** подключения модели: это
   единственный кусок, который обязан быть безошибочным.
3. **Промпт и агент `tusur`** — `~/.config/opencode/agents/tusur.md`
   (primary, `model: router/fast`, `steps: 60`, edit только в проекте,
   остальное `ask`), плюс `prompts/plan.md` с правилами стабильности.
4. **`plan.sh` + systemd-таймер** — `opencode run --agent tusur --model
   router/fast --format json --auto`, затем валидатор, затем `notify.py`.
5. **Оценки трудоёмкости** — отдельным проходом: новое задание из фида →
   метка `est-*` + шаги, запись в Vikunja (кэшируется, повторно не считается).
   До этого — проверить, что метки Vikunja ходят через CalDAV как `CATEGORIES`.
5a. **Календарный вид плана** — решить: Gantt в Vikunja или отдельный приватный
   `.ics` с блоками как `VEVENT` (у `ics.py` генератор уже есть). Сетки-календаря
   в Vikunja нет (`list/gantt/table/kanban`), VEVENT она не понимает.
6. **Личный календарь (Google, секретный iCal-адрес)** — читать занятые вечера и
   вычитать из окон. Адрес даёт пользователь, кладём в
   `~/.config/tusur/google-calendar.url` (600); парсим `VEVENT`, берём только
   интервалы `DTSTART..DTEND` (без названий — они не нужны и не сохраняются).
   **Статус: адрес не получен** — пользователь отложил, код не пишем.
   CalDAV/OAuth не нужны: записывать в личный календарь мы не собираемся.
7. **Приёмник вебхуков** — локальный HTTP на `127.0.0.1:8787`, пользователь
   создаёт проектный вебхук в UI; проверить, что Vikunja не режет localhost.

Критерий приёмки: два прогона подряд на неизменных данных дают **ноль**
переносов во втором; искусственно сломанный план (блок поверх пары) отклоняется
валидатором с внятной причиной; при провале валидатора старый план остаётся.

Параметры получены: окно 10:00–00:00 включая выходные, догоны — воскресенье,
оценка — метка `est-*` по эвристике, личный календарь читаем, вебхук ставит
пользователь. Ждёт ответа только одно: какой сервис держит личный календарь.

## Грабли (из проверок и разбора)

| Грабли | Как обходить |
|---|---|
| Блокировка IP за частоту: ~15 быстрых запросов → TCP-таймаут всего домена | пауза 2–3 с, ≤10 запросов подряд, кэш HTML, обновление раз в 6 ч |
| Недели вперёд пустые | расписание публикуют волнами; пустая неделя — норма, не ошибка |
| Префикс `/ocenka/` у `course_links` | без него 404; полный путь `/ocenka/api/v1/lessons/<id>/course_links` |
| Moodle сворачивает строки **табом** | разворачивать `\r\n[ \t]`, а не только `\r\n ` |
| Время в фиде — UTC | Томск +7; в `.ics` писать `TZID=Asia/Tomsk` с фиксированным `+0700` |
| `preset_time=all` → 303 | рабочее окно `recentupcoming` (~60 дней), опрашивать регулярно |
| Смена UID ломает подписку | UID = `<lesson_id>-<дата-время>@timetable.tusur.ru` |
| `raw.githubusercontent.com` отдаёт `text/plain` | подписываться только на `github.io` |
| GitHub отключает scheduled workflow после 60 дней без активности | коммиты бота считаются активностью; раз в 2 месяца ручной запуск |
| IP раннеров — датацентры (Azure, общий на тысячи проектов) | первый запуск только `workflow_dispatch`; при таймауте — локальный таймер, генератор тот же |
| `state.json` не переживает смену машины | SEQUENCE из закоммиченного `.ics` (`--state-from`), состояние = сам файл |
| Крон Actions: задержка 5–30 мин, редкие пропуски | для расписания терпимо; не строить на нём напоминания «за 5 минут» |
| Google кэширует фид 8–24 ч | не ждать мгновенных правок в Google; Apple/Яндекс обновляются чаще |
| `materials/` read-only для агентов | пишет только `tools/sdo_import.py` |
| authtoken календаря = пароль на чтение | файл 600, никогда в git и чат; при утечке — перевыпуск |
| 2FA в ЛК ТУСУР (не проверено) | влияет на авто-релогин; при включённой 2FA — ручной вход раз в N дней |

## Открытые вопросы

Отвечено: публичность репозитория (публичный, `Z0DEN/tusur-schedule`),
приложение-планировщик (**Vikunja**), заметки (не нужны), доставка `.ics`
(GitHub Pages), **сборка и публикация — GitHub Actions** (локального `push` нет).

Ждут ответа:

1. **`deadlines.ics` в публичном репозитории?** Расписание там безобидно, а в
   дедлайнах — полные тексты заданий из закрытой СДО. Предложение: держать их
   вне публичного репо (локально/Tailscale) либо отдельным приватным контуром.
2. **Корпуса**: где проходят физкультура (ЭДпФКиС) и ОПД — в расписании
   аудитория не указана; нужен корпус и время в пути от УЛК.
3. **2FA** в кабинете ТУСУРа — влияет на срок жизни сессии СДО.
4. **Рабочее окно дня** для планировщика (07:30–23:00? до скольки реально).
5. **Оценки трудоёмкости**: доверяем эвристике по типу или задаёшь коэффициент
   на предмет.
6. **Читать ли личный календарь** (CalDAV) ради вычитания занятых вечеров.
7. **Оценки и посещаемость** (`ocenka`, `attendance`) — берём или нет.
8. **OCR формул** (`pix2tex`/`nougat`, ~2 ГБ) — только если появятся сканы.
9. **Привязка Vikunja**: оставить порт на `0.0.0.0` или только Tailscale +
   localhost.
10. **Формат уведомлений**: только календарь/телефон или ещё сообщения ассистента.
