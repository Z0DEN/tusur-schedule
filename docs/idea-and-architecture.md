# Идея и архитектура

Дата фиксации: 2026-11-17. Документ описывает замысел целиком; проверенные
факты и команды — в `verified-facts.md`, порядок работ — в `implementation-plan.md`.

## 1. Зачем

Ассистент должен сам, без ручных действий:

1. **Знать расписание** группы 735-1 и держать его в календаре устройства.
2. **Собирать дедлайны** СДО: тесты закрываются, лабораторные и задания «должно
   быть выполнено», с полным текстом условия.
3. **Скачивать материалы курсов** (лекции, методички) и складывать их туда,
   откуда их читают решающие агенты.
4. **Напоминать** о важном: пара через 30 минут, дедлайн через N часов,
   «появилось новое задание», «срок сдвинулся».
5. **Отдавать данные в `math-solver`**: условия задач в LaTeX и лекции в
   `materials/` — чтобы расчёты шли по реальным материалам, а не по памяти.
6. В перспективе — **строить план работ** (что и когда делать с учётом пар и
   дедлайнов) и выгружать его в приложение-планировщик. Приложение ещё не
   выбрано; формат обмена определим позже.

Исходная формулировка пользователя (заметка OpenChamber): асинхронно или по
команде обновлять задания и сообщения преподавателей, считывать дедлайны,
скачивать файлы-приложения к заданиям, получать расписание группы и из всего
этого составлять оптимальное расписание работ; оно уходит в приложение
планирования. Расписание пар учитывается при планировании, но это отдельная
сущность от плана домашних работ.

## 3. Архитектура

Три независимых конвейера, общий формат состояния и общие артефакты.

```
                ┌──────────────────────────────────────────────┐
                │ 1. РАСПИСАНИЕ (публичный, HTML/JSON)         │
                │ fetch week_id=850.. → parser.py → Lesson[]   │
                └───────────────┬──────────────────────────────┘
                                │
                ┌───────────────▼──────────────────────────────┐
                │ 2. ДЕДЛАЙНЫ (ICS-фид СДО, authtoken)         │
                │ fetch feed → ics_feed.py → Event[] + state   │
                └───────────────┬──────────────────────────────┘
                                │
                ┌───────────────▼──────────────────────────────┐
                │ ics.py → schedule-735-1.ics / deadlines.ics  │
                │          + diff.json (что изменилось)        │
                └───────────────┬──────────────────────────────┘
                                │
        ┌───────────────────────┴────────────────────────┐
        │ GitHub Pages (постоянный https)                │
        │ подписка в календаре + уведомления из диффа    │
        └────────────────────────────────────────────────┘

                ┌──────────────────────────────────────────────┐
                │ 3. МАТЕРИАЛЫ (нужна сессия SSO)              │
                │ storageState → файлы курсов → tools/sdo_import.py
                │ → math-solver/materials/<предмет>/ + INDEX.md │
                └──────────────────────────────────────────────┘
```

### 3.1 Расписание

- Источник: страница группы `https://timetable.tusur.ru/faculties/fb/groups/735-1`,
  при необходимости `?week_id=N`.
- Список недель (23 шт.) берётся с той же страницы: `week_id`, номер, чётность,
  дата начала.
- Парсим **мобильные таблицы** `table.table-lessons.visible-xs` — по одной на день;
  desktop-сетка неудобна.
- Каждая пара: `span.hidden` = id, `abbr[title]` = полное название,
  `span.kind` = вид занятия, `span.auditoriums` + `title` вложенной ссылки =
  аудитория и корпус, `span.group` = преподаватель.
- **Модалка** `div.js-lesson-info-modal[data-lesson-id]` — источник истины:
  абсолютная дата `18.11.2026`, время `13:15-14:50`, аудитория, ФИО, группы,
  `data-course-links-url`.
- Курс СДО для пары: `GET /ocenka/api/v1/lessons/<id>/course_links` →
  `[{"url":"https://sdo.tusur.ru/auth/edu?id=12911","anchor":"Курс (гр. 735-1)"}]`.
  Префикс **`/ocenka/`** обязателен, без него 404.

### 3.2 Дедлайны

- Источник: `https://sdo.tusur.ru/calendar/export_execute.php?userid=…&authtoken=…&preset_what=all&preset_time=recentupcoming`
- Рабочее окно: `recentupcoming` (~60 дней вперёд, 19 событий на момент проверки).
  `preset_time=all` сайт не отдаёт (303).
- `CATEGORIES` = предмет (`ЧМ`, `Организация ЭВМ и вычислительных систем`, `ЭиС 1`).
- `SUMMARY` = «Тест "…" закрывается», «Лабораторная работа №1 — срок сдачи».
- `DESCRIPTION` = **полный текст задания**, формулы уже в LaTeX, ссылки на лекции.
- Время в UTC; UID стабильны (`242267@sdo.tusur.ru`) → годятся для диффа.
- Хранение ссылки: `~/.config/tusur/calendar.url`, права 600, в git не попадает.

### 3.3 Материалы (этап, требующий сессии)

- Вход: SSO `profile.tusur.ru` → `storageState` Playwright (пароль не храним,
  человек логинится сам в открытом окне).
- Далее либо `core_course_get_contents` через `/lib/ajax/service.php?sesskey=…`
  (тот же JSON-API, что использует веб-интерфейс), либо скачивание файлов по
  ссылкам из курса.
- Выход: `~/opencode/math-solver/materials/<предмет>/` + строка в `INDEX.md`
  силами `tools/sdo_import.py`.

## 4. Контракты

### 4.1 `.ics`

- `UID` стабильный: `<lesson_id>-<YYYYMMDDTHHMM>@timetable.tusur.ru` для пар,
  UID фида как есть для дедлайнов. Смена UID = дубли в календаре.
- `SEQUENCE` растёт только при изменении содержимого (сравнение хеша payload).
- `TZID=Asia/Tomsk` + `VTIMEZONE` с фиксированным `+0700` (перехода нет с 2014).
- `VALARM` −30 минут на пары; для дедлайнов — настраиваемый набор (−1 день, −3 часа).
- Свёртка строк ≤75 октетов, CRLF.

### 4.2 Состояние

- `state.json`: `uid → {hash, seq}` — для `SEQUENCE`.
- `cache/`: сырой HTML страниц недель и фид — чтобы пересобирать без сети.
- `diff.json`: `{new: [...], changed: [...], gone: [...]}` — вход для уведомлений.

### 4.3 Материалы для `math-solver`

- Формат строки `INDEX.md`: `предмет | путь к файлу | что там`.
  «Что там» — **описание + примеры формул**, не выжимка лекции (заметка
  пользователя: агент решает по оригиналу или расшифровке).
- Основной источник для расчётов — текст с формулами в LaTeX (`.md`), рядом
  лежит исходный PDF как оригинал.
- Папка `materials/` read-only для агентов; пишет только скрипт-импортёр.

## 5. Доставка и расписание обновлений

**Решение (пользователь, 2026-11-17): собирает и публикует GitHub Actions**, а не
таймер на ноутбуке. Локального `git push` нет вообще — коммит делает сам workflow
своим `GITHUB_TOKEN`. Причина: файл обновляется, даже когда ноутбук выключен, и
не требует, чтобы машина была в сети по расписанию.

- **GitHub Pages**: репозиторий `tusur-schedule`, `schedule-735-1.ics` в корне
  ветки `main`, Pages = Deploy from a branch.
- Ссылка подписки: `https://z0den.github.io/tusur-schedule/schedule-735-1.ics`
  (постоянная; меняется содержимое, не адрес).
- **Workflow** `.github/workflows/update.yml`: `schedule` `0 1 * * *` (UTC) =
  08:00 по Томску + `workflow_dispatch` для ручной проверки,
  `permissions: contents: write`, concurrency-группа, шаги: checkout →
  `pip install` → `main.py` → `git diff --quiet && exit 0` → commit + push.
- **В облако уходит только расписание.** Дедлайны, `diff.json` и план остаются
  локальными: в них тексты заданий из закрытой СДО. Поэтому `authtoken` фида в
  `Settings → Secrets` **не нужен вовсе** — риск утечки снят, этап 2 упрощён.
- **`deadlines.ics` в прежнем виде не нужен**: дедлайны идут задачами в Vikunja,
  напоминания даёт Tasks.org. Если когда-нибудь понадобится отдельный `.ics` с
  дедлайнами — он живёт на Tailscale, а не в репозитории.
- **Состояние — сам файл.** SEQUENCE берётся из уже закоммиченного `.ics`
  (`--state-from`), поэтому `state.json` между раннером и ноутбуком не
  рассинхронизируется и лишний файл в репозитории не нужен.
- **Граница «облако / локально»**: публичное (расписание группы) — в Actions;
  личное — только локально. Vikunja живёт на `100.121.145.104:3456` в Tailscale
  и из облака недоступна, материалы лекций — файлы на ноутбуке, приватный
  `deadlines.ics` — вне публичного репозитория.
- Периодичность в календаре задаёт клиент: Apple 30–60 мин, Google 8–24 ч.

### 5.0 Риски облачного запуска (проверяются первым `workflow_dispatch`)

| Риск | Что делать |
|---|---|
| IP раннера GitHub (Azure, общий на тысячи проектов) может быть закрыт для `timetable.tusur.ru` — сайт блокирует по IP после ~15 быстрых запросов | первый запуск только вручную; при таймауте остаётся локальный таймер с тем же генератором |
| Крон Actions неточен: задержка 5–30 мин, редкие пропуски; после 60 дней без активности расписания отключаются | терпимо для расписания; при отключении — push в репозиторий или ручной запуск |
| Фикстура нужна в CI | `fixtures/` **не** в `.gitignore`: там публичная страница, личных данных нет, зато проверка «3 события» воспроизводима на чистом клоне |
| `DTSTAMP` меняется каждый прогон → ежедневный пустой коммит | читать предыдущий `.ics`; если payload не изменился — переиспользовать его `DTSTAMP`, файл остаётся побайтово тем же |

Локальный `systemd`-таймер остаётся **резервным** путём (и единственным для
Vikunja и материалов): генератор тот же, отличается только способ доставки.

### 5.1 Как работает подписка (и чем отличается от импорта)

`.ics` — текстовый формат iCalendar (RFC 5545). Внутри `VEVENT` с `UID`,
`DTSTART/DTEND`, `SUMMARY`, `LOCATION`, `DESCRIPTION` и блоками `VALARM`
(напоминание за N минут до начала).

| | Импорт файла | Подписка по URL |
|---|---|---|
| Как | открыть `.ics` один раз | добавить `https://…` или `webcal://…` в календарь |
| Обновления | нет | клиент сам перезапрашивает тот же URL |
| Перенос/отмена пары | не подхватится | подхватится после обновления |
| Редактирование | можно | только чтение |
| Частота | — | задаётся клиентом (Apple от 5 мин, Google без настройки) |

Ссылка **статична**: меняется содержимое файла, а не адрес. Пересоздавать
подписку нужно только при смене способа доставки. Событие, исчезнувшее из фида,
при подписке пропадает из календаря — так и обрабатывается отмена пары.

### 5.2 Отвергнутые способы доставки

Рассматривались и отброшены по решению пользователя (оставлен GitHub Pages):

- **Tailscale** (`http://100.121.145.104:8000/…`) — приватно и стабильно, но
  Google Calendar не принимает непубличный http;
- **локальная сеть** (`http://192.168.0.106:8000/…`) — только дома, нужен
  закреплённый IP;
- **облако/Nextcloud** — лишний посредник, ссылка тоже публичная, но менее
  предсказуемая по кэшу.

## 7. Планировщик и задачи: Vikunja

Третий контур («куда складывать план работ») реализован на **Vikunja 2.8.0**:
self-hosted, Docker, SQLite, порт 3456, доступ по Tailscale.

Роли двух протоколов — их легко перепутать, поэтому явно:

| | `.ics`-подписка | CalDAV |
|---|---|---|
| Что | пары и дедлайны, **только чтение** | мои задачи, **чтение и запись** |
| Кто пишет | наш скрипт из фида СДО и расписания | агент (через MCP/REST) и человек (в приложении) |
| Куда | GitHub Pages → календарь телефона | Vikunja |
| Зачем | напоминания о парах и сроках | планирование работ и отметки «готово» |

MCP Vikunja — третий вход, только для диалога с агентом («что на неделе»,
«создай задачу»). Данные при этом одни и те же: MCP, REST и CalDAV смотрят в
одну базу.

### 7.1 Структура задач

- **Проект = предмет** (`ЧМ`, `ТВиМС`, `Физика`, `Методы оптимизации`, `ЭиС`,
  `Иностранный`, `ОПД`, «Цифровая кафедра»). `Inbox` — временный приёмник.
- **Задача = один дедлайн из фида**: `SUMMARY` → заголовок, `DESCRIPTION` →
  описание (markdown, формулы уже в LaTeX), `DTSTART` → дата выполнения,
  `CATEGORIES` → проект, `UID` → внешний ключ для идемпотентности.
- **Оценка трудоёмкости — метка** `est-3h` из фиксированной лестницы
  (`est-0.5h … est-12h`): пользовательских полей в Vikunja нет (проверено по
  схеме `Task.json`), а метку удобно менять в приложении. Оценка, отличающаяся
  от записанной в `plan.json`, считается правкой человека и замораживается.
  Подробности — `docs/vikunja-integration.md` §2.
- **Шаги задания** (45–90 мин) создаются как подзадачи или как отдельные задачи
  с суффиксом `#1…#n`, чтобы их можно было ставить в разные дни.
- **Метки**: `горит`, `лаб`, `тест`, `экзамен` — для фильтров и цвета.

### 7.2 Планирование (решение 2026-11-17: план составляет ИИ, вариант D)

Пользователь выбрал: **план составляет модель раз в сутки**, и при этом агент
должен уметь **всё, что умеет приложение** — приоритет, метки, цвет, вложения,
связи, даты, напоминания. Поэтому запись разделена на два класса:

| Что делает агент | Через что | Проверка |
|---|---|---|
| приоритет, цвет, метки, описание, комментарии, связи, исполнители, повторение, перенос между проектами | **Vikunja MCP напрямую** | не нужна: это данные задачи, а не план |
| дата сдачи дедлайна | **Vikunja MCP напрямую** | не нужна: это факт из фида |
| **слоты работы** (`start_date`/`due_date` блоков) | **`plan_apply`** (наш инструмент) | обязательна |
| вложения, напоминания | **наш инструмент** | в Vikunja MCP их нет |

Слот блока — единственное, что может сломать расписание. Всё остальное —
обогащение задачи, его можно писать свободно и откатывать по одному полю.

```
systemd-таймер (локально, раз в сутки утром)
 └─ plan.sh
    1. build_context.py → .state/plan-input.json
         свободные окна на 14 дней (пары, буферы, личные события),
         открытые дедлайны, текущий план, ограничения, pinned
    2. opencode run --agent tusur --model router/fast --format json --auto
         агент обогащает задачи через Vikunja MCP, затем:
         plan_check(blocks) → нарушения → правит → снова check
         plan_apply(blocks) → запись слотов, обновление plan.json, diff
    3. notify.py → diff.json («что изменилось и почему»)
```

`plan_check` ничего не пишет и нужен, чтобы агент сам себя проверял до записи;
`plan_apply` отказывает, если нарушения остались, и возвращает их текстом —
агент исправляет и повторяет (не больше 3 итераций, дальше прогон считается
провальным и план не меняется).

**Наш тонкий MCP `tusur`** (не ядро, а надстройка) даёт четыре инструмента:
`plan_check`, `plan_apply`, `task_attach` (загрузка файла), `task_remind`
(напоминание). Причина: в каталоге Vikunja MCP **нет** создания вложений и
**нет** работы с напоминаниями — проверено по списку 57 действий.

**Защиты:**

- **Два токена Vikunja.** `planner` — без права удаления задач (дневной прогон не
  должен уметь стирать), `interactive` — полный, для работы в чате.
- **Аудит.** На каждый блок агент пишет комментарий «поставлено планировщиком:
  причина». В Vikunja видно, почему слот здесь.
- **`plan.json`** хранит, что записал агент (слоты, метки, оценки) — по нему
  считается churn и определяется, что изменил человек.
- **`pinned`** проверяется в `plan_apply`, а не в промпте: инструмент отказывает,
  даже если модель уверена, что «так лучше».

**Валидатор — то, что защищает план от недетерминизма модели.** Он не
оптимизирует, а делит проверки на два класса: жёсткие (нарушение = отказ) и
мягкие (нарушение = флаг в уведомлении, план применяется).

| Жёсткие | Мягкие |
|---|---|
| пересечение с парой, с личным событием, между блоками | ≤ 3 ч одного предмета в день |
| вне окна 10:00–00:00 | загрузка дня ≤ 60 % свободного времени |
| блок короче 45 мин или длиннее 2 ч | буфер ≥ 24 ч до срока |
| `pinned` изменён | ≤ 3 переносов за прогон |
| дубли ID (`sdo-<uid>#<n>`) | «воскресенье без новых блоков» |
| перерыв между блоками < 10 мин | |

Правила, которые иначе конфликтуют друг с другом:

- **Длинные задания.** Лимит часов предмета в день считается как
  `cap = max(3 ч, est/2)`, но не больше 5 ч. Для `est-4h` это 3 ч в день и второй
  день; для `est-12h` — 5 ч, иначе курсовая не планируется никогда.
- **Воскресенье.** Новых задач не ставим. Разрешены только блоки **уже
  существующих** задач со сроком ≤ 7 дней: максимум 2 блока и не больше 3 часов
  суммарно. Это и есть «догоны», а не пустой день.
- **Буфер до срока.** По умолчанию ≥ 24 ч. Если окон не хватает — не меньше 6 ч,
  с меткой `горит` и отдельной строкой в уведомлении. Иначе правило само себя
  блокирует на дедлайнах в понедельник утром.
- **Churn** считается по «сегодня и завтра»: там ≤ 3 переносов. Дальше двух дней
  план пересобирается свободно — эти слоты пользователь ещё не видел.
- **Поместимость.** Перед раскладкой: если нужных часов больше 60 % доступных
  окон до ближайшего срока, планировщик не «оптимизирует», а пишет
  `не помещается: N часов` и предлагает, чем жертвовать (сначала тесты с близким
  сроком).

Нарушение жёсткого правила → агент получает список нарушений и правит, до 3
итераций. После третьей неудачи план не применяется, остаётся предыдущий,
приходит уведомление с причиной.

**Рабочее окно** (решение пользователя 2026-11-17): **10:00–00:00, включая
выходные**. Утро до
10:00 не планируется вообще; блоки 22:00–00:00 разрешены, поэтому 24-часовой
буфер до срока проверяется жёстко; блок не начинается, если до границы окна
меньше его длительности. День для правила «не больше 3 часов предмета»
считается по дню начала блока.

**Откуда оценки:** только эвристика, её ставит сам агент (тест 40–60 мин, лаба
3–4 ч, задание с LaTeX 1.5–2 ч, курсовая 8–12 ч) — пользователь правит метку
`est-*` в приложении, и при расхождении с `plan.json` пересборка идёт под новое
число, а оценка замораживается.

**Как узнаём об изменениях:** опрос Vikunja по фильтру `updated > курсор`
(проверено), интервал 5–10 минут, debounce 2–5 минут. Вебхуки Vikunja есть, но
через API-токен недоступны (`401`), настраиваются только руками в UI — пользователь
включит проектный вебхук сам, локальный приёмник проверяется на практике.
Опрос остаётся страховкой, если вебхук не доедет.

**Занятое время** (решение 2026-11-17): пары и личное живут в Google Calendar,
план — в Vikunja. Планировщик читает пары из своего источника (подписка Google
отстаёт на 8–24 ч) и личные события из Google; пишет только в Vikunja. Полная
схема — `docs/unified-view.md` §8.

Личный календарь — **Google Calendar**, читаем его
**секретным iCal-адресом** (Settings → календарь → «Secret address in iCal
format»). Причина: нам нужно только чтение занятых интервалов, а секретный адрес
даёт это без OAuth, без проекта в Google Cloud, без пароля приложения и без 2FA.
Хранится как пароль: файл 600, в git не попадает, в чат не печатается.
Задержка обновления у Google — от 5 минут до нескольких часов, для планирования
это приемлемо. CalDAV/OAuth нужны были бы только ради записи в календарь —
писать мы туда не собираемся.

**Правила стабильности** (иначе задачи «прыгают» и плану перестаёшь верить):
модель получает текущий план и обязана сохранять слоты, которые не противоречат
новым данным; менять можно только при причине — новый дедлайн, отмена пары,
просрочка, просьба пользователя. Все прочие переносы считаются churn и
отклоняются валидатором.

**Ограничения по данным:** коэффициент реализма 0.6, буфер 24 часа до срока,
`pinned` не двигать, **день на догоны — воскресенье** (без новых блоков, туда
переезжает недоделанное), «пора начинать» = начало первого блока, а не только
срок.

**Стоимость:** один прогон ~0.3–1 ₽ (fast, 6–10 шагов), 10–30 ₽ в месяц;
эскалация на `claude-haiku-5.5` только после провала валидатора.

**Календарный вид.** В Vikunja сетки-календаря нет: видов ровно четыре —
`list`, `gantt`, `table`, `kanban` (проверено по схеме `ProjectView.json`).
`VEVENT` Vikunja не знает, только задачи с датами. Поэтому «увидеть план как
календарь» решается либо Gantt'ом внутри Vikunja, либо нашим отдельным
приватным `.ics` с блоками плана как `VEVENT` (генератор уже есть). Подробнее —
`docs/vikunja-integration.md` §7 и `docs/unified-view.md`.

Ограничения CalDAV, которые надо помнить: канбан-колонки и вложения по нему не
ходят, HTML-описания приезжают текстом, напоминания нельзя дублировать в двух
местах.

## 8. Чего в архитектуре сознательно нет

- Скрейпинга личного кабинета СДО для дедлайнов — фид дешевле и стабильнее.
- Хранения пароля Moodle/ТУСУР — только `storageState` после ручного входа.
- Ежечасного опроса расписания — сайт блокирует за частоту.
- Дублирования `materials/` внутри проекта: материалы живут в `math-solver`.
- Двусторонней синхронизации календаря и Vikunja: календарь — проекция в одну
  сторону, источник истины — Vikunja (иначе конфликты двух систем).
- Полноценного MCP-сервера `tusur` как ядра: данные — это файлы и Vikunja, а MCP
  нужен только для интерактивных запросов.
- Заметочного сервиса: заметки не нужны, материалы лежат файлами в `materials/`.
- Своего Android-приложения: телефон работает через CalDAV-клиент.
