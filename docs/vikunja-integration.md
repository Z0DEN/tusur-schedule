# Vikunja: механика интеграции (проверено 2026-11-17)

Зачем этот файл: планировщик пишет план в Vikunja и читает оттуда правки
пользователя. Здесь — что Vikunja реально умеет, где хранить данные, как узнавать
об изменениях и как не перетирать друг друга. Все утверждения — из ответов API
2.8.0 на этом инстансе, команды в `verified-facts.md`.

## 1. Поля задачи: чего в них нет

Схема `GET /api/v2/schemas/Task.json` (полный список полей):

```
assignees, attachments, bucket_id, buckets, comment_count, comments,
cover_image_attachment_id, created, created_by, deleted_at, deleted_by,
description, done, done_at, due_date, end_date, hex_color, id, identifier,
index, is_favorite, is_unread, labels, percent_done, position, positions,
priority, project_id, reactions, related_tasks, reminders, repeat_after,
repeat_mode, start_date, subscription, time_entries_count, title, updated
```

Отсюда два важных вывода:

1. **Пользовательских полей нет** — отдельного `estimate_min` в Vikunja негде
   завести. Оценку храним в служебной строке описания: `est=180 src=ai`.
2. **Автора последнего изменения нет** — есть `created_by` (кто создал) и
   `updated` (когда), но не «кто изменил». Значит «агент или человек» придётся
   выводить из сравнения со своим `plan.json`, а не из API.

Есть `time_entries_count` — учёт времени в Vikunja существует, и в будущем
фактические часы можно писать туда вместо оценок. Сейчас не используем.

## 2. Как хранить оценку трудоёмкости (решение: метка)

Пользователь выбрал править оценку **меткой**, а не строкой в описании: в
Tasks.org метку видно и менять её проще, чем текст описания.

Лестница меток (создаются один раз в проекте, фиксированные):

```
est-0.5h  est-1h  est-1.5h  est-2h  est-3h  est-4h  est-6h  est-8h  est-12h
```

- На задаче висит **ровно одна** метка `est-*`. Две и больше — ошибка ввода:
  берём наибольшую, в уведомление пишем «на задаче две оценки».
- Оценка ставится агентом при первом разборе задания; человек меняет метку в
  приложении.
- **`src` выводится из сравнения с `plan.json`**, а не хранится явно: метка
  отличается от той, что записал агент → это правка человека → оценка заморожена
  (`src=user`), агент её не пересчитывает, только раскладывает по слотам.
- Нет метки → задача считается неоценённой, агент ставит метку сам.
- Дискретность — цена выбора: «180 минут» превращается в `est-3h`. Для
  планирования этого достаточно (слоты всё равно кратны 30 минутам), но точные
  значения вроде 2 ч 20 мин так не выразить.

Что проверить перед реализацией: переносятся ли метки Vikunja в CalDAV как
`CATEGORIES` VTODO и обратно. Если да — правка метки в Tasks.org доедет до
планировщика; если нет — придётся читать правки через API и просить менять
оценку в веб-интерфейсе Vikunja.

Резервный вариант, если метки через CalDAV не поедут: строка `est=180 src=ai`
в описании (описание через CalDAV ходит точно).

## 3. Как узнать, что что-то изменилось

| Способ | Статус | Детали |
|---|---|---|
| **Опрос по `updated`** | **проверено, работает** | фильтр `updated > <метка времени>` отдаёт только изменённое: `tasks_list {filter: "updated > now-1h"}` → 1 задача сразу после создания |
| **Webhook Vikunja** (проект) | существует, но **не через наш токен** | `GET /api/v1/projects/1/webhooks` → `401` с MCP-токеном, при этом `/api/v1/projects/1` → `200`. Похоже, что вебхуки и `/api/v1/user` недоступны для API-токенов (только JWT). Создаются руками в UI: проект → Settings → Webhooks |
| **User webhook** (напоминания, просрочки) | существует | там же, в настройках аккаунта; для планировщика не нужен |

Вывод для реализации: **основа — опрос**. Webhook не отменяется, но настроить его
можно только руками в интерфейсе, и остаётся непроверенным, принимает ли Vikunja
цель `http://127.0.0.1:PORT` (защита от SSRF может запретить localhost).

Опрос: раз в 5–10 минут, курсор = максимальный `updated` из прошлого прогона
(хранить в `.state/cursor.json`), плюс debounce 2–5 минут, чтобы перетаскивание
трёх задач подряд дало один пересчёт.

## 4. Кто есть кто: различение правок

Механизм (без опоры на API, которого нет):

1. `plan.json` хранит, что агент записал в прошлый раз: `id`, `slots`,
   `est`, `title`, `due`, время записи.
2. Задача изменилась → сравниваем с `plan.json`:
   - изменил агент сам (запись в текущем прогоне) → событие игнорируется, иначе
     получится цикл «записал → увидел → пересобрал»;
   - значение отличается от агентского → это человек → `pin` на текущий прогон;
   - `done: true` → вывести из плана, часы вернуть в окна;
   - задача исчезла (удалена) → записать в `plan.json` «отклонено», не
     восстанавливать из фида.
3. `pin` снимается, когда срок прошёл, задача выполнена или пользователь
   попросил пересобрать целиком.

Слабое место: если человек и агент поменяли одно и то же поле в одну минуту,
правка может быть принята за агентскую. Лечится тем, что `pin` ставится по
любому расхождению, а не только по факту «не наша запись».

## 5. Особенности MCP-инструментов Vikunja (нашли на практике)

| Что | Как правильно |
|---|---|
| Создание задачи | `tasks_create {project: 1, title: …, description: …}` — поле называется **`project`**, не `project_id` |
| Чтение/правка/удаление | `tasks_read {task: 2}`, `tasks_update {task: 2, …}`, `tasks_delete {task: 2}` — **`task`**, не `id` |
| Фильтры | `&&` / `||`, никаких `and`/`or`; даты — абсолютные или `now+24h`, `now/d+1d` |
| Описания | по умолчанию HTML; для markdown передавать `format: "markdown"` |
| Удаление | `tasks_delete` убирает задачу из выдачи (`title like …` → 0), но в API есть `deleted_at` — то есть soft-delete |

## 6. Что осталось непроверенным

1. Принимает ли Vikunja webhook на `127.0.0.1` (SSRF-защита) — проверяется только
   с реально созданным вебхуком.
2. Можно ли дать API-токену права на вебхуки (создание токена — действие
   пользователя в UI).
3. CalDAV-токен не создан → синхронизация с Tasks.org не проверена, поведение
   правок с телефона (время `updated`, конфликты) — неизвестно.
4. Как Vikunja ведёт себя при одновременной записи из CalDAV и API (конфликт
   версий) — не проверялось.

## 7. Календарный вид: чего в Vikunja нет (проверено)

Схема `ProjectView.json` перечисляет ровно четыре вида:

```
view_kind: ["list", "gantt", "table", "kanban"]
```

На инстансе это подтверждается живым списком представлений проекта `Inbox`:
`List`, `Gantt`, `Table`, `Kanban`. **Сетки-календаря (месяц/неделя) в Vikunja
нет**, и «событий» (`VEVENT`) она не знает вообще — только задачи (`VTODO`) с
датами `start_date` / `due_date` / `end_date`.

Что есть вместо календаря:

| Что | Что показывает |
|---|---|
| **Gantt** | ближайшее к календарю: задачи полосами по датам, перетаскивание работает |
| **Table** | даты колонками, сортировка по сроку |
| **Kanban** | стадии, дат не показывает |
| Дашборд «Upcoming» | список ближайших задач по дате, не сетка |

### Три способа получить именно календарь

1. **Gantt внутри Vikunja** — ничего не делать, но это не «сетка недели».
2. **CalDAV + календарное приложение, умеющее VTODO** — Tasks.org показывает
   списки, сетку не рисует; кандидаты на сетку с задачами: aCalendar (через
   OpenTasks/DAVx⁵), jtx Board. **Не проверено** — надо смотреть на телефоне.
3. **Наш собственный `.ics` с блоками плана как `VEVENT`** — тогда блоки
   «ср 19:00–20:30 решить пункты 1–2» видны в любом календаре нативно, вместе с
   парами. Генератор `VEVENT` у нас уже есть (`ics.py`). Минус: в блоке будет
   название задания, то есть это **приватные данные** — в публичный репозиторий
   такой файл класть нельзя, нужна приватная доставка (Tailscale-сервер или
   отдельный контур).

Вариант 3 — единственный, который даёт настоящую сетку на телефоне и не зависит
от того, умеет ли конкретное приложение рисовать VTODO.
